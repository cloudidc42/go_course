## 1. ทำไมการมีส่วนร่วมใน Open Source ถึงเร่งการเติบโตของนักพัฒนา

ตลอด 108 บทที่ผ่านมา เราเรียนรู้ Go ผ่านตัวอย่างที่ออกแบบมาเพื่อการสอน — โค้ดสั้น กระชับ เน้นแนวคิดเดียวชัดเจนต่อครั้ง แต่โค้ด production จริงของโปรเจกต์อย่าง **Kubernetes**, **Docker**, **Prometheus**, หรือแม้แต่ standard library ของ Go เอง **ไม่ได้ถูกออกแบบมาเพื่อสอนใคร** มันถูกออกแบบมาเพื่อ**แก้ปัญหาจริงที่ซับซ้อน** ภายใต้ข้อจำกัดจริง (performance, backward compatibility, edge case ที่สะสมมาจากผู้ใช้นับล้าน) — การอ่านและมีส่วนร่วมในโค้ดแบบนี้คือก้าวถัดไปที่หลักสูตรใดๆ ในโลกให้ไม่ได้ครบเท่ากับการลงมือทำจริง

เหตุผลที่การ contribute เร่งการเติบโตได้เร็วกว่าการเขียนโปรเจกต์ส่วนตัวคนเดียว:

### 1.1 ได้อ่านโค้ดคุณภาพสูงระดับ Production

โค้ดของโปรเจกต์ open source ที่มีผู้ใช้จำนวนมากผ่านการ**รีวิวมาแล้วหลายรอบโดยผู้เชี่ยวชาญหลายคน** — การไล่อ่าน source code ของ `net/http` หรือ `encoding/json` ใน Go standard library เอง (สิ่งที่หลักสูตรนี้แนะนำให้ทำตั้งแต่หลายบทก่อนหน้า เช่นตอนอธิบาย `database/sql` ใน **Part 078**) สอนอะไรมากมายที่ไม่มีในตำรา: วิธีจัดการ edge case, วิธีออกแบบ API ให้ backward compatible, วิธีเขียน error message ที่มีประโยชน์จริง

### 1.2 ได้รับ Feedback จากคนที่เก่งกว่า

Code review บน pull request ของโปรเจกต์ใหญ่มักมาจาก **maintainer ที่มีประสบการณ์นับสิบปี** — ได้รับคอมเมนต์ตรงจากคนเหล่านี้ (แม้จะเป็นแค่ typo หนึ่งจุดในเอกสาร) มีค่ามากกว่าการอ่านหนังสือหลายเล่ม เพราะเป็น feedback ที่**เจาะจงกับโค้ดที่เราเขียนจริง**

### 1.3 ได้ฝึกทำงานร่วมกับคนที่ไม่รู้จักกันมาก่อน

ต่างจากงานในทีมที่คุ้นเคยกัน การ contribute ให้โปรเจกต์ open source ฝึกทักษะ**สื่อสารทางเทคนิคกับคนแปลกหน้าที่มีบริบทต่างกันโดยสิ้นเชิง** ต้องอธิบายปัญหา แนวทางแก้ และเหตุผลให้ชัดเจนพอที่คนไม่เคยรู้จักกันจะเข้าใจและเชื่อถือได้ — ทักษะนี้ถ่ายทอดตรงไปยังการทำงานในบริษัทข้ามทีมข้ามไทม์โซนได้ทันที

### 1.4 สร้าง Portfolio ที่ตรวจสอบได้จริง

Pull request ที่ถูก merge เข้าโปรเจกต์ที่มีชื่อเสียงคือ**หลักฐานเชิงประจักษ์**ที่แข็งแรงกว่า resume ทั่วไปมาก เพราะใครก็ตรวจสอบได้ทันทีว่าโค้ดจริงเป็นอย่างไร ผ่าน review process จริงอย่างไร และแก้ปัญหาอะไรจริง — หลายบริษัทให้น้ำหนักกับ GitHub contribution history ไม่น้อยไปกว่าประวัติการทำงาน

## 2. หา "First Issue" ที่เหมาะกับตัวเอง

อุปสรรคแรกที่คนส่วนใหญ่เจอไม่ใช่เรื่องเทคนิค แต่คือ **"จะเริ่มจากตรงไหนดี"** — โปรเจกต์ใหญ่มี codebase เป็นแสนบรรทัด รู้สึกท่วมท้นเกินกว่าจะเริ่ม แนวทางที่ได้ผลจริง:

### 2.1 มองหา Label มาตรฐาน

โปรเจกต์ open source ส่วนใหญ่ (โดยเฉพาะบน GitHub) ติด label พิเศษไว้สำหรับ issue ที่เหมาะกับผู้เริ่มต้น:

- **`good first issue`** — label มาตรฐานที่ GitHub เองส่งเสริมให้ใช้ทั่ว ecosystem บ่งชี้ว่า maintainer ประเมินแล้วว่าเหมาะกับคนที่ไม่เคยแตะ codebase นี้มาก่อน
- **`help wanted`** — บ่งชี้ว่า maintainer ต้องการความช่วยเหลือจริง ไม่ได้แค่รู้ปัญหาแต่ยังไม่มีเวลาทำเอง
- **`documentation`** — งานปรับปรุงเอกสาร มักไม่ต้องเข้าใจ codebase ลึกมาก เหมาะเป็นจุดเริ่มต้นที่ได้เรียนรู้โครงสร้างโปรเจกต์ไปพร้อมกัน

ค้นหาข้าม repository จำนวนมากพร้อมกันได้ผ่าน GitHub search โดยตรง เช่น `is:issue is:open label:"good first issue" language:go` เพื่อกรองเฉพาะโปรเจกต์ Go

### 2.2 เริ่มจากโปรเจกต์ที่ใช้งานอยู่แล้วในชีวิตจริง

วิธีที่ได้ผลดีกว่าการค้นหา label แบบสุ่มคือ **เริ่มจาก dependency ที่ใช้อยู่แล้วในโปรเจกต์ของตัวเอง** — ถ้าเคยเจอบั๊กเล็กๆ หรือเอกสารที่อ่านแล้วงงตอนใช้ library ตัวหนึ่ง นั่นคือโอกาส contribute ที่ดีที่สุด เพราะมี**บริบทจริง**อยู่แล้วว่าปัญหาคืออะไร ทำไมถึงสำคัญ และวิธีแก้ที่ถูกต้องควรเป็นอย่างไร ต่างจากการไปหยิบ issue ของโปรเจกต์ที่ไม่เคยใช้มาก่อนซึ่งต้องเสียเวลาทำความเข้าใจบริบทเพิ่มมาก

### 2.3 ประเภทงานที่เหมาะกับมือใหม่

| ประเภทงาน | ความยาก | ตัวอย่าง |
|---|---|---|
| แก้ typo/ปรับปรุงเอกสาร | ต่ำมาก | แก้ doc comment ที่อธิบายผิด, เพิ่มตัวอย่างโค้ดใน README |
| เพิ่ม test case ที่ยังขาด | ต่ำ-กลาง | เพิ่ม table-driven test case สำหรับ edge case ที่ยังไม่มี test คลุม (ทบทวน **Part 034**) |
| แก้บั๊กเล็กที่มี reproduction ชัดเจน | กลาง | บั๊กที่มีคนรายงานพร้อมโค้ดที่ทำซ้ำปัญหาได้แล้ว |
| เพิ่ม feature เล็กที่มี design ชัดเจนแล้ว | กลาง-สูง | maintainer อนุมัติแนวทางแล้ว รอแค่คนลงมือ implement |
| ปรับ architecture หรือเพิ่ม feature ใหญ่ | สูง | ควรทำหลังสร้างความน่าเชื่อถือกับ maintainer แล้วเท่านั้น |

หลักปฏิบัติที่ดีสำหรับ pull request แรกในโปรเจกต์ใดก็ตาม: **เริ่มเล็ก** เสมอ ไม่ว่าจะเก่งแค่ไหนก็ตาม เพราะ PR แรกมีจุดประสงค์แฝงคือ**การทำความรู้จักกับ workflow และมาตรฐานของโปรเจกต์นั้น** ไม่ใช่แค่การแก้ปัญหาให้ใหญ่ที่สุดเท่าที่จะทำได้

### 2.4 ถ้ายังไม่มี Issue ที่ตรงกับปัญหาที่เจอ: เขียน Bug Report ที่ดีก่อน

บางครั้งจุดเริ่มต้นการ contribute ไม่ใช่การไปหยิบ issue ที่มีอยู่แล้ว แต่คือ**การเจอปัญหาเองแล้วรายงานให้ถูกวิธี** — bug report ที่ดีมีค่ามากพอๆ กับ PR ที่แก้บั๊กนั้น เพราะช่วยให้ maintainer หรือ contributor คนอื่นแก้ปัญหาได้เร็วขึ้นมาก โครงสร้างที่ใช้ได้ผล:

```markdown
## What happened
`client.Fetch(ctx, url)` คืน error `context deadline exceeded` ทันที
แม้จะตั้ง `ctx` ด้วย timeout 30 วินาที และ endpoint ปกติตอบภายใน 2 วินาที

## What I expected
`Fetch` ควรใช้ timeout ที่ตั้งไว้ใน `ctx` จริง ไม่ควร timeout เร็วกว่านั้น

## Reproduction
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()
	_, err := client.Fetch(ctx, "https://httpbin.org/delay/2")
	// err: context deadline exceeded (ควรจะสำเร็จ)

## Environment
- go version go1.24.7 linux/amd64
- library version: v1.3.0
```

องค์ประกอบที่ทำให้ bug report มีคุณภาพ: **ขั้นตอนทำซ้ำปัญหาได้จริง (reproduction)** ด้วยโค้ดที่ copy ไปรันได้ทันที, **บอกพฤติกรรมที่คาดหวังกับที่เกิดขึ้นจริงแยกกันชัดเจน**, และ **ระบุ environment ครบ** (เวอร์ชัน Go, เวอร์ชัน library, OS ถ้าเกี่ยวข้อง) — bug report ที่ขาดข้อมูลเหล่านี้มักถูก maintainer ขอข้อมูลเพิ่มก่อนจะแก้ได้ ทำให้เสียเวลาไปมาหลายรอบโดยไม่จำเป็น

## 3. Contribution Workflow มาตรฐาน: Fork, Branch, Commit, PR

โปรเจกต์ Go ส่วนใหญ่บน GitHub (ยกเว้นตัว Go project เองที่จะพูดถึงในหัวข้อ 8) ใช้ workflow แบบ **fork-and-pull-request** มาตรฐานเดียวกับ open source ทั่วไป:

```bash
# 1. Fork repository ผ่านหน้าเว็บ GitHub (กดปุ่ม Fork) จะได้ copy ของ repo ในบัญชีตัวเอง

# 2. Clone fork ของตัวเองลงเครื่อง
git clone https://github.com/yourusername/some-project.git
cd some-project

# 3. เพิ่ม remote ของ repository ต้นฉบับไว้อ้างอิง (เรียกตามธรรมเนียมว่า "upstream")
git remote add upstream https://github.com/original-owner/some-project.git

# 4. สร้าง branch ใหม่สำหรับงานนี้โดยเฉพาะ — ห้ามทำงานบน main/master ตรงๆ
git checkout -b fix-nil-pointer-in-parser

# 5. แก้ไขโค้ด, commit เป็นก้อนเล็กๆ ที่มีความหมายชัดเจนแต่ละ commit
git add internal/parser/parser.go
git commit -m "parser: fix nil pointer dereference when input is empty"

# 6. ก่อน push ให้ sync กับ upstream เสมอ ป้องกัน conflict สะสม
git fetch upstream
git rebase upstream/main

# 7. Push ขึ้น fork ของตัวเอง
git push origin fix-nil-pointer-in-parser

# 8. เปิด Pull Request จากหน้าเว็บ GitHub: จาก fork ของเราไปยัง repository ต้นฉบับ
```

### หลักปฏิบัติสำคัญของแต่ละขั้นตอน

- **ตั้งชื่อ branch ให้สื่อความหมาย** ไม่ใช่ `fix`, `update`, `patch-1` เฉยๆ — ชื่อที่ดีบอกได้ทันทีว่า branch นี้ทำอะไร
- **Commit message ควรอธิบาย "ทำไม" ไม่ใช่แค่ "ทำอะไร"** — โค้ด diff บอกอยู่แล้วว่าเปลี่ยนบรรทัดไหน แต่ commit message ต้องบอกเหตุผลที่ diff อยู่ในรูปแบบนี้ หลายโปรเจกต์ Go (รวมถึงตัว Go เอง) ใช้ธรรมเนียม `<package>: <คำอธิบายสั้นแบบ imperative mood>` เช่น `parser: fix nil pointer dereference when input is empty` (สังเกตรูปแบบ "fix" ไม่ใช่ "fixed" หรือ "fixes" — ธรรมเนียมนี้มาจาก git เองที่มองว่า commit คือ "คำสั่ง" ที่บอกว่าจะทำอะไรกับ codebase)
- **`rebase` แทน `merge` เมื่อ sync กับ upstream** (ในโปรเจกต์ที่นิยม linear history) เพื่อให้ประวัติ commit อ่านง่าย ไม่มี merge commit รกๆ ปนอยู่ — แต่ต้องเช็คธรรมเนียมของแต่ละโปรเจกต์ก่อนเสมอ (หัวข้อ 7)

## 4. เตรียมโค้ดให้พร้อมก่อนเปิด PR: `gofmt`, `go vet`, Tests

ก่อนเปิด pull request ทุกครั้ง มีเช็คลิสต์ขั้นต่ำที่ต้องทำเอง**ก่อน**ให้คนอื่นเห็นโค้ด — การส่ง PR ที่ไม่ผ่านขั้นตอนพื้นฐานเหล่านี้ทำให้ reviewer เสียเวลาชี้จุดที่เครื่องมือตรวจจับได้เองอยู่แล้ว และสร้างความประทับใจที่ไม่ดีตั้งแต่ต้น

```bash
# 1. Format โค้ดตามมาตรฐาน Go เสมอ (Part 001) — ไม่มีข้อยกเว้น ไม่มีการถกเถียงเรื่อง style
gofmt -l .          # แสดงไฟล์ที่ format ไม่ตรงมาตรฐาน (ควรว่างเปล่า)
gofmt -w .          # แก้ไขให้ตรงมาตรฐานอัตโนมัติ

# 2. ตรวจจับข้อผิดพลาดเชิง logic ที่ compiler จับไม่ได้ (Part 001, 086)
go vet ./...

# 3. รัน linter ของโปรเจกต์เอง (ถ้ามี ปกติระบุไว้ใน CONTRIBUTING.md — Part 086)
golangci-lint run ./...

# 4. รัน test ทั้งหมดให้ผ่าน รวมถึง race detector (Part 044)
go test -race ./...

# 5. ถ้าเพิ่ม public function/type ใหม่ ตรวจสอบว่ามี doc comment ตามธรรมเนียม (Part 008)
go doc ./... | less
```

### ทำไมต้องทำเองก่อนเสมอ แม้โปรเจกต์จะมี CI อยู่แล้ว

หลายคนคิดว่า "มี CI ตรวจอยู่แล้ว ปล่อยให้ CI จับก็ได้" — แต่นี่เป็นการใช้เวลาของ maintainer และ CI resource ของโปรเจกต์อย่างไม่ให้เกียรติ **CI ควรเป็นด่านสุดท้ายที่ยืนยันซ้ำ ไม่ใช่ด่านแรกที่ใช้หาข้อผิดพลาดพื้นฐาน** — maintainer ที่เห็น PR ที่ผ่านทุกอย่างเรียบร้อยตั้งแต่แรกจะมีแนวโน้มให้ความสนใจกับเนื้อหาจริงของโค้ดมากกว่า และมีแนวโน้ม merge เร็วกว่า PR ที่ต้องแก้ CI failure ไปมาหลายรอบ

## 5. เขียน Pull Request Description ที่ดี

PR description คือจุดแรกที่ maintainer ใช้ตัดสินใจว่าจะให้ความสำคัญกับ PR นี้แค่ไหน — โครงสร้างที่ใช้ได้ผลกับเกือบทุกโปรเจกต์:

```markdown
## What
แก้ nil pointer dereference ใน `parser.Parse()` เมื่อ input string เป็นค่าว่าง

## Why
Issue #234 รายงานว่า `parser.Parse("")` ทำให้แอปพลิเคชัน crash แทนที่จะคืน error
```

### องค์ประกอบที่ทำให้ PR description มีคุณภาพ

- **อ้างอิง issue number เสมอ** (`Fixes #234`) — GitHub จะปิด issue อัตโนมัติเมื่อ PR ถูก merge ถ้าใช้ keyword ที่ถูกต้อง (`Fixes`, `Closes`, `Resolves`)
- **อธิบาย "ทำไม" ไม่ใช่แค่ "อะไร"** — โค้ด diff ที่แนบมากับ PR แสดง "อะไร" อยู่แล้ว สิ่งที่ diff บอกไม่ได้คือเหตุผลเบื้องหลังการตัดสินใจนั้น
- **บอกว่า test อย่างไร** — ทำให้ reviewer มั่นใจได้ทันทีว่ามีการยืนยันจริง ไม่ใช่แค่ "น่าจะทำงาน"
- **ถ้าเป็น breaking change ให้บอกตรงๆ ตั้งแต่ต้น** เชื่อมโยงกับหลักการ SemVer ที่ **Part 108** สอนไว้ — maintainer ต้องรู้ล่วงหน้าเพื่อวางแผนว่าจะรวมเข้า MINOR หรือต้องรอ MAJOR version ถัดไป

## 6. รับ Feedback จาก Code Review อย่างสร้างสรรค์

นี่คือทักษะที่แยกคนที่ contribute ได้ต่อเนื่องระยะยาว ออกจากคนที่ท้อและเลิกไปหลัง PR แรก — Code review ในโปรเจกต์ที่มีคุณภาพมักมีคอมเมนต์เยอะ **แม้กับโค้ดที่ดีอยู่แล้ว** เพราะ maintainer ที่ดีจะรักษามาตรฐานของ codebase ให้สม่ำเสมอ

### หลักปฏิบัติที่ควรยึดถือ

1. **อย่าตีความคอมเมนต์เป็นเรื่องส่วนตัว** — คอมเมนต์เกี่ยวกับโค้ด ไม่ใช่เกี่ยวกับความสามารถของผู้เขียน แม้แต่ maintainer ที่เก่งที่สุดก็เคยได้รับคอมเมนต์แบบนี้มาก่อนตอนเริ่มต้น
2. **ถามกลับเมื่อไม่เข้าใจ แทนที่จะเดา** — ถ้าคอมเมนต์ไม่ชัดเจนว่าต้องแก้อย่างไร ถามตรงๆ ใน thread นั้นเลย เช่น "ขอบคุณสำหรับ feedback ครับ ผมสงสัยว่าคุณหมายถึงให้ย้าย logic นี้ไปที่ package ไหน หรือแค่เปลี่ยนชื่อฟังก์ชัน?" — maintainer ส่วนใหญ่ยินดีอธิบายเพิ่มเสมอ
3. **แก้ทีละคอมเมนต์ แล้ว reply ยืนยัน** — เมื่อแก้ตามคอมเมนต์แล้ว ให้ reply กลับใน thread นั้น (เช่น "แก้แล้วครับ" พร้อมลิงก์ commit ที่แก้) เพื่อให้ reviewer ติดตามง่ายว่าคอมเมนต์ไหนแก้แล้วบ้าง
4. **ถ้าไม่เห็นด้วยกับคอมเมนต์ ให้อธิบายเหตุผลอย่างสุภาพ ไม่ใช่เพิกเฉย** — บางครั้ง reviewer มองข้ามบริบทบางอย่างไป การอธิบายเหตุผลกลับไปอย่างมีข้อมูลรองรับเป็นเรื่องปกติและได้รับการต้อนรับในวัฒนธรรม open source ที่ดี ตราบใดที่ทำด้วยความสุภาพและเปิดใจรับฟัง ไม่ใช่ยืนกรานแบบไม่มีเหตุผล
5. **เตรียมใจว่า PR อาจถูกขอให้แก้หลายรอบ หรือถูกปฏิเสธ** — นี่คือเรื่องปกติมาก แม้แต่ maintainer ระดับสูงของโปรเจกต์ดังก็เคยมี PR ถูกขอแก้ซ้ำหลายรอบ การถูกปฏิเสธไม่ได้แปลว่าล้มเหลว แต่เป็นส่วนหนึ่งของกระบวนการรักษาคุณภาพของ codebase

## 7. ก่อนลงมือเขียนโค้ด: เปิด Discussion บน Issue ก่อนเสมอสำหรับงานที่ไม่เล็ก

ความผิดพลาดที่พบบ่อยรองจากการข้าม `gofmt`/`go vet` คือ **การเขียนโค้ดเสร็จเรียบร้อยแล้วค่อยเปิด PR โดยไม่เคยคุยกับ maintainer มาก่อนเลย** สำหรับ typo หรือบั๊กเล็กๆ วิธีนี้ไม่มีปัญหา แต่สำหรับ feature ใหม่หรือการแก้ไขที่มีหลายวิธีเป็นไปได้ วิธีนี้เสี่ยงสูงมากที่จะเสียเวลาไปโดยเปล่าประโยชน์

### ทำไมต้องคุยก่อน

ลองนึกภาพว่าใช้เวลาทั้งสุดสัปดาห์เขียน feature หนึ่งอย่างตั้งใจ แล้วเปิด PR ไป สิ่งที่อาจเกิดขึ้นได้คือ maintainer ตอบกลับว่า **"ขอบคุณสำหรับความตั้งใจ แต่เรามีแผนจะแก้ปัญหานี้ด้วยวิธีอื่นอยู่แล้ว"** หรือ **"feature นี้ไม่ตรงกับทิศทางของโปรเจกต์"** — ความผิดหวังแบบนี้ป้องกันได้เกือบทั้งหมดด้วยการ**เปิด issue ถามก่อนลงมือ**:

```markdown
สวัสดีครับ ผมสนใจจะ implement retry ที่ configurable backoff strategy
ให้ package นี้ (อ้างอิงจาก issue #120)

แนวทางที่ผมคิดไว้คือเพิ่ม interface `BackoffStrategy` แล้วให้ `Client`
รับ option ผ่าน functional options pattern

ก่อนเริ่มเขียนโค้ดจริง อยากถามว่าแนวทางนี้สอดคล้องกับทิศทางที่ทีมต้องการไหมครับ
หรือมีข้อจำกัดอะไรที่ควรรู้ก่อนไหมครับ
```

คอมเมนต์แบบนี้ใช้เวลาไม่กี่นาที แต่ป้องกันการเสียเวลาหลายชั่วโมงหรือหลายวันได้อย่างสมบูรณ์ — maintainer ส่วนใหญ่ยินดีตอบคำถามแบบนี้เร็วกว่าการรีวิว PR ขนาดใหญ่ที่ไม่ตรงทิศทางมาก

### สัญญาณที่บอกว่าควรคุยก่อนแน่นอน

- เพิ่ม public API ใหม่ (function, type, package)
- เปลี่ยนพฤติกรรมของโค้ดที่มีอยู่แล้ว แม้จะไม่ breaking ก็ตาม
- แก้ปัญหาที่ยังไม่มี issue อยู่ก่อน (ควรเปิด issue อธิบายปัญหาก่อนเสมอ แยกจาก PR)
- งานที่คาดว่าจะใช้เวลาเขียนมากกว่าสองสามชั่วโมง

ในทางกลับกัน งานเล็กมาก (แก้ typo, เพิ่ม test case ที่ไม่กระทบ behavior) ไม่จำเป็นต้องขอ approval ก่อนเสมอไป — เปิด PR ตรงๆ ได้เลยตามความเหมาะสม

## 8. อ่าน `CONTRIBUTING.md` ของโปรเจกต์จริงให้เป็นนิสัย

ก่อนเริ่มเขียนโค้ดแม้แต่บรรทัดเดียว **ให้อ่านไฟล์ `CONTRIBUTING.md`** (หรือ `docs/CONTRIBUTING.md`, `.github/CONTRIBUTING.md` แล้วแต่โปรเจกต์) เสมอ — ไฟล์นี้คือ "กติกาเฉพาะ" ของแต่ละโปรเจกต์ ที่มักต่างจากธรรมเนียมทั่วไปในรายละเอียด แม้จะใช้ workflow fork-and-PR แบบเดียวกันก็ตาม

สิ่งที่ `CONTRIBUTING.md` ของโปรเจกต์ Go คุณภาพดีมักระบุไว้:

- **รูปแบบ commit message ที่โปรเจกต์นั้นต้องการ** (บางโปรเจกต์ใช้ [Conventional Commits](https://www.conventionalcommits.org/) เช่น `fix:`, `feat:`, `docs:` นำหน้า — บางโปรเจกต์มีธรรมเนียมของตัวเอง)
- **ต้องเซ็น Contributor License Agreement (CLA) หรือไม่** — โปรเจกต์ขององค์กรใหญ่ (Google, CNCF) มักต้องการให้เซ็น CLA ก่อน PR แรกจะถูกพิจารณา (มักมี bot อัตโนมัติเช็คให้ตอนเปิด PR)
- **วิธีรัน test suite ในเครื่อง** โดยเฉพาะถ้าต้องมี dependency ภายนอก (database, message queue) ที่ต้องตั้งค่าก่อน
- **นโยบายเรื่อง breaking change** — บางโปรเจกต์ไม่รับ PR ที่ breaking API เลยนอกจาก maintainer หลักเป็นคนตัดสินใจเอง
- **Code of Conduct** — เกือบทุกโปรเจกต์ที่จริงจังมีเอกสารนี้ กำหนดมาตรฐานพฤติกรรมในการสื่อสารภายในชุมชน

### ตัวอย่างความแตกต่างที่พบจริงระหว่างโปรเจกต์

Kubernetes ต้องการให้ contributor เซ็น CLA ผ่าน [Google's CLA process](https://cla.developers.google.com/) และมีขั้นตอน review ที่ซับซ้อนกว่าปกติ (ต้องมี `/lgtm` และ `/approve` จาก reviewer คนละบทบาทกัน ผ่านระบบ [Prow](https://prow.k8s.io) ของตัวเอง) ในขณะที่ library เล็กๆ ของนักพัฒนาคนเดียวอาจแค่ต้องการให้ fork, แก้, แล้วเปิด PR ตรงๆ โดยไม่มีขั้นตอนพิเศษใดๆ เลย — **ไม่มี "มาตรฐานเดียว" ที่ใช้ได้กับทุกโปรเจกต์** การอ่าน `CONTRIBUTING.md` ก่อนเสมอคือวิธีเดียวที่แน่ใจได้ว่าทำตามกติกาที่ถูกต้อง

## 9. ข้อควรรู้เฉพาะของชุมชน Go: Gerrit ของ Go เอง vs GitHub PR ของโปรเจกต์ทั่วไป

นี่คือจุดที่มือใหม่ในชุมชน Go มักสับสน: **การ contribute ให้ตัวภาษา Go เอง (repository `golang/go`) ใช้ workflow ที่ต่างจากโปรเจกต์ Go ทั่วไปบน GitHub อย่างสิ้นเชิง**

### โปรเจกต์ Go ทั่วไป (Kubernetes, Gin, Cobra, ฯลฯ): GitHub PR ตามปกติ

โปรเจกต์ Go เกือบทั้งหมดที่ไม่ใช่ตัวภาษา Go เอง — รวมถึงโปรเจกต์ที่เรียนไปตลอดหลักสูตรนี้อย่าง Gin, Echo, Fiber, gorilla/mux, GORM — ใช้ **GitHub Pull Request** แบบมาตรฐานตามที่อธิบายในหัวข้อ 3-6 ทุกประการ

### ตัวภาษา Go เอง (`golang/go`): Gerrit + `golang.org/x/review/git-codereview`

โปรเจกต์ Go เองใช้ **[Gerrit](https://go-review.googlesource.com)** ซึ่งเป็นระบบ code review ที่ Google พัฒนาขึ้นเอง (ใช้ภายใน Google มาก่อน Go จะเกิดด้วยซ้ำ) แม้ issue tracker ยังคงอยู่บน GitHub (`github.com/golang/go/issues`) แต่**การ review โค้ดจริงเกิดขึ้นที่ Gerrit ไม่ใช่ GitHub** ความแตกต่างสำคัญที่ต้องรู้ก่อนลอง contribute ให้ตัวภาษา:

- **หนึ่ง commit คือหนึ่ง "Change" ที่ review แยกกัน** ไม่ใช่การรวม commit หลายอันเข้า PR เดียวแบบ GitHub — แนวคิดนี้ใกล้เคียงกับที่ Google ใช้ภายในองค์กรทั้งหมด
- **ต้องติดตั้งเครื่องมือเสริม `golang.org/x/review/git-codereview`** ซึ่งเพิ่มคำสั่ง git ใหม่ (`git codereview change`, `git codereview mail`) เพื่อส่ง change ไปที่ Gerrit แทนการ `git push` ตรงๆ ไปยัง GitHub
- **ต้องเซ็น Google CLA ก่อนเสมอ** เพราะ contribution จะกลายเป็นส่วนหนึ่งของ Go source ที่ Google ดูแลลิขสิทธิ์ร่วม
- **Reviewer ให้คะแนนแบบ `Code-Review +1/+2/-1/-2`** แทนการ approve/request-changes แบบ GitHub และการ merge เข้า `master` ทำผ่านระบบอัตโนมัติของ Gerrit เอง ไม่ใช่ปุ่ม "Merge" แบบ GitHub

> **ทำไม Go เลือกใช้ Gerrit แทน GitHub PR ทั้งที่ hosting หลักคือ GitHub**: เหตุผลหลักคือ Go เป็นโปรเจกต์ที่มีปริมาณ commit สูงมากและต้องการ workflow ที่รองรับ **stacked changes** (การแก้ไขที่ต่อเนื่องกันเป็นชุด แต่ละอันพึ่งพา change ก่อนหน้า) ได้ดีกว่า GitHub PR ในยุคที่ Go เริ่มออกแบบระบบนี้ไว้ (ก่อน GitHub PR จะพัฒนาฟีเจอร์ที่ตอบโจทย์นี้ได้ดีเท่าปัจจุบัน) และเพราะทีม Go core หลายคนคุ้นเคยกับ Gerrit จากการทำงานที่ Google อยู่แล้ว

รายละเอียดขั้นตอนแบบเต็มมีอยู่ใน [go.dev/doc/contribute](https://go.dev/doc/contribute) ซึ่งเป็นจุดเริ่มต้นที่ถูกต้องที่สุดสำหรับใครที่อยากลองส่ง patch แรกให้ตัวภาษา Go เอง — บทเรียนสำคัญที่ควรจำจากหัวข้อนี้คือ **อย่าสมมติว่า workflow ของโปรเจกต์หนึ่งใช้ได้กับทุกโปรเจกต์ในภาษาเดียวกัน** แม้แต่ในกรณีที่โปรเจกต์นั้นคือตัวภาษาเองก็ตาม

## 10. Go Proposal Process: เมื่อการเปลี่ยนแปลงกระทบตัวภาษาเอง

การแก้บั๊กเล็กๆ ใน `golang/go` ใช้ workflow Gerrit ตามหัวข้อ 8 ตรงๆ ได้เลย แต่เมื่อการเปลี่ยนแปลงกระทบ **ตัวภาษา, standard library API สาธารณะ, หรือ tooling ที่มีผลกว้าง** (เช่น การเพิ่ม generics ใน Go 1.18 ที่ **Part 001** กล่าวถึง) ต้องผ่านกระบวนการที่เข้มงวดกว่ามากที่เรียกว่า **[Go Proposal Process](https://go.dev/s/proposal-process)**

ขั้นตอนคร่าวๆ ของ proposal process:

1. **เปิด issue บน GitHub พร้อม label `Proposal`** อธิบายปัญหาที่ต้องการแก้และแนวทางที่เสนอ
2. **Proposal Review Committee** (กลุ่ม maintainer หลักของ Go) พิจารณาเบื้องต้นว่าควรเข้าสู่กระบวนการอภิปรายแบบเต็มหรือปฏิเสธตั้งแต่ต้น (proposal จำนวนมากถูกปฏิเสธในขั้นนี้ด้วยเหตุผลว่าขัดกับปรัชญาความเรียบง่ายของภาษา)
3. **ช่วงอภิปรายสาธารณะ** ที่ใครก็ตามในชุมชนแสดงความเห็นได้บน issue นั้น มักกินเวลาหลายเดือนถึงหลายปีสำหรับการเปลี่ยนแปลงใหญ่ (ข้อเสนอสำหรับ generics เองถูกอภิปรายต่อเนื่องมานานกว่า 10 ปีก่อนจะถูกยอมรับ ตามที่ **Part 001** กล่าวถึง)
4. **ตัดสินใจ**: `Accepted` (เข้าสู่การ implement จริง), `Declined` (ปฏิเสธพร้อมเหตุผล), หรือ `Likely Accept/Decline` (ช่วงรอความเห็นค้านสุดท้ายก่อนตัดสินใจจริง)
5. **Implementation**: เมื่อ accepted แล้ว การ implement จริงจะเข้าสู่ workflow Gerrit ปกติตามหัวข้อ 8

### บทเรียนที่ได้จากกระบวนการนี้

กระบวนการที่ดูช้าและเข้มงวดนี้**ไม่ใช่ความไร้ประสิทธิภาพ** แต่เป็นการป้องกัน **Go 1 Compatibility Promise** (**Part 001, 108**) โดยตรง — เมื่อ feature ใดถูกเพิ่มเข้าภาษาแล้ว มันจะต้องอยู่ตลอดไปและ**แก้ไขย้อนหลังไม่ได้**อีกเลยโดยไม่ทำลายสัญญานั้น การพิจารณาอย่างละเอียดถี่ถ้วนก่อนตัดสินใจจึงคุ้มค่ากว่าการรีบเพิ่ม feature แล้วต้องแบกรับผลที่ตามมาไปตลอดกาล — นี่คือปรัชญา **"less is more"** ที่นำมาใช้ในระดับกระบวนการตัดสินใจของทั้งภาษา ไม่ใช่แค่ในระดับ syntax เท่านั้น

## 11. จาก Contributor สู่ Maintainer: เมื่อถึงเวลาดูแลโปรเจกต์เอง

หลัง contribute ให้โปรเจกต์หนึ่งอย่างต่อเนื่องสักระยะ (แก้บั๊กหลายอัน, ตอบคำถามคนอื่นใน issue, รีวิว PR ของคนอื่นแม้ไม่มีสิทธิ์ merge) บางครั้ง maintainer เดิมจะเชิญให้เป็น **collaborator** หรือ **maintainer** ร่วม — นี่คือก้าวถัดไปตามธรรมชาติของเส้นทางที่ **Part 110** จะพูดถึงในฐานะหนึ่งในเส้นทางอาชีพ (open source maintainer)

### สิ่งที่เปลี่ยนไปเมื่อกลายเป็น Maintainer

บทบาทเปลี่ยนจาก "คนส่ง PR" ไปเป็น "คนตัดสินใจ" ทักษะที่ต้องเพิ่มเข้ามา:

- **Triage issue ใหม่ที่เข้ามา** — จัดลำดับความสำคัญ, ติด label ที่เหมาะสม (`good first issue`, `bug`, `enhancement`), ปิด issue ที่ซ้ำกันหรือไม่เกี่ยวข้อง
- **รีวิว PR ของคนอื่นอย่างสร้างสรรค์** — ใช้หลักการเดียวกับหัวข้อ 6 แต่กลับด้าน: ตอนนี้เป็นฝ่ายให้ feedback ต้องระวังคำพูดให้สุภาพและอธิบายเหตุผลชัดเจน ไม่ใช่แค่บอกว่า "ผิด"
- **ตัดสินใจเรื่อง roadmap และ breaking change** — ต้องใช้หลักการ SemVer จาก **Part 108** อย่างมีวินัย เพราะการตัดสินใจของ maintainer กระทบผู้ใช้ทุกคนของ library โดยตรง
- **ดูแลสุขภาพของชุมชน** — ตอบคำถามให้เร็วพอสมควร (แม้จะแค่ "ขอบคุณ เดี๋ยวดูให้ครับ"), บังคับใช้ Code of Conduct อย่างเสมอภาค

### รับมือกับความขัดแย้งในชุมชนอย่างมืออาชีพ

ความขัดแย้งเกิดขึ้นได้เสมอในชุมชนที่มีคนจำนวนมาก ตั้งแต่การถกเถียงเรื่อง design ไปจนถึงพฤติกรรมที่ไม่เหมาะสมของสมาชิกบางคน หลักปฏิบัติที่ maintainer ที่ดีใช้:

1. **แยกความเห็นต่างทางเทคนิคออกจากพฤติกรรมที่ไม่เหมาะสม** — การเถียงกันเรื่อง API design เป็นเรื่องปกติและมีประโยชน์ ตราบใดที่ทุกฝ่ายสุภาพและมีเหตุผลรองรับ
2. **อ้างอิง Code of Conduct อย่างสม่ำเสมอ ไม่เลือกปฏิบัติ** — บังคับใช้กฎเดียวกันไม่ว่าผู้ฝ่าฝืนจะเป็นใคร รวมถึงตัว maintainer เองด้วย
3. **ตัดสินใจที่ยาก บางครั้งต้องทำคนเดียว** — สุดท้ายแล้ว maintainer ต้องรับผิดชอบต่อทิศทางของโปรเจกต์ บางการตัดสินใจไม่มีทางทำให้ทุกคนพอใจได้ สิ่งที่ทำได้คือ**อธิบายเหตุผลอย่างโปร่งใส**แม้จะไม่มีใครเห็นด้วยทั้งหมดก็ตาม

## 12. เริ่มต้น Open Source Library ของตัวเองให้ดีตั้งแต่วันแรก

นอกจาก contribute ให้โปรเจกต์คนอื่นแล้ว การเริ่มต้น library ของตัวเองเป็น open source ก็เป็นก้าวสำคัญของการเติบโต หัวข้อนี้รวบรวมทุกอย่างที่หลักสูตรนี้สอนไว้แล้วให้เป็น checklist เดียวสำหรับวันแรกที่เปิด repository

### 12.1 README ที่ดี

README คือ**หน้าตาแรก**ที่ตัดสินว่าคนจะลองใช้ library หรือไม่ ภายใน 30 วินาทีแรก โครงสร้างที่ใช้ได้ผล:

```markdown
# mylib

[![Go Reference](https://pkg.go.dev/badge/example.com/mylib.svg)](https://pkg.go.dev/example.com/mylib)
[![CI](https://github.com/user/mylib/actions/workflows/ci.yml/badge.svg)](https://github.com/user/mylib/actions)

คำอธิบายสั้นหนึ่งประโยคว่า library นี้ทำอะไร แก้ปัญหาอะไร

## Install

	go get example.com/mylib

## Usage

	package main

	import "example.com/mylib"

	func main() {
		result := mylib.DoSomething()
	}

## Documentation

รายละเอียดเต็มดูที่ [pkg.go.dev](https://pkg.go.dev/example.com/mylib)

## License

MIT — ดูไฟล์ [LICENSE](./LICENSE)
```

องค์ประกอบที่ขาดไม่ได้: **badge สถานะ CI และลิงก์ไป pkg.go.dev** (สร้างความน่าเชื่อถือทันทีที่เห็น), **ตัวอย่างโค้ดที่ copy ไปรันได้ทันที** ไม่ใช่แค่คำอธิบายลอยๆ, และ **บอกวิธีติดตั้งด้วย `go get` ตรงๆ**

### 12.2 Doc Comment ที่เป็นมิตรกับ `go doc` (ทบทวน Part 008)

**Part 008** สอนธรรมเนียม doc comment ไปแล้ว — สำหรับ library สาธารณะ นี่ไม่ใช่ทางเลือกแต่คือ**ข้อบังคับเชิงคุณภาพ** เพราะหน้า `pkg.go.dev` ของ library ถูกสร้างขึ้นอัตโนมัติจาก doc comment ในโค้ดโดยตรง — ทุก exported identifier ต้องมี comment ที่ขึ้นต้นด้วยชื่อของมันเองตามธรรมเนียม:

```go
// Client คือ HTTP client ที่ห่อ retry logic และ timeout ที่เหมาะสมไว้ให้อัตโนมัติ
//
// ใช้ New เพื่อสร้าง Client ใหม่ ไม่ควรสร้างผ่าน struct literal ตรงๆ
// เพราะ zero value ของ Client ยังไม่มี HTTP transport ที่ถูกตั้งค่า
type Client struct {
	// ...
}

// New สร้าง Client ใหม่พร้อมค่า default ที่เหมาะกับการใช้งานทั่วไป
func New(opts ...Option) *Client {
	// ...
}
```

### 12.3 Semantic Versioning ตั้งแต่ v0 (ทบทวน Part 108)

เริ่ม tag เวอร์ชันตั้งแต่ `v0.1.0` เร็วที่สุดเท่าที่จะทำได้ (แม้ API จะยังไม่นิ่ง — v0.x.x ตาม SemVer คือช่วงที่ **อนุญาตให้ breaking change ได้โดยไม่ต้องขึ้น major version** เพราะยังไม่ถือว่าเสถียร) เมื่อ API เริ่มนิ่งแล้วค่อยออก `v1.0.0` อย่างเป็นทางการ — การมีเวอร์ชันตั้งแต่ต้นทำให้ผู้ใช้กล้า `go get` ไปทดลองใช้ได้ทันที แทนที่จะต้องพึ่ง commit hash ที่ไม่มีความหมายอะไรเลย

### 12.4 CI ตั้งแต่ Commit แรก (ทบทวน Part 098)

ตั้ง GitHub Actions workflow พื้นฐาน (`go build`, `go vet`, `go test -race`, `golangci-lint`) ตั้งแต่ commit แรกของ repository ไม่ใช่รอให้โปรเจกต์ใหญ่ขึ้นก่อนค่อยเพิ่ม — CI badge สีเขียวบน README ตั้งแต่ต้นสร้างความน่าเชื่อถือ และป้องกัน regression ตั้งแต่ commit ที่สองเป็นต้นไป

### 12.5 ไฟล์ LICENSE

**ไม่มีไฟล์ LICENSE เท่ากับไม่มี license ให้ใครใช้งานได้ตามกฎหมาย** แม้ repository จะเป็น public บน GitHub ก็ตาม — ผู้ใช้ที่ระมัดระวังทางกฎหมาย (โดยเฉพาะบริษัท) จะไม่กล้าใช้ library ที่ไม่มีไฟล์ license ชัดเจนเลย license ที่นิยมในวงการ Go:

| License | ลักษณะ |
|---|---|
| **MIT** | เปิดกว้างที่สุด อนุญาตแทบทุกการใช้งานรวมถึงเชิงพาณิชย์ เป็นที่นิยมที่สุดใน Go ecosystem |
| **Apache 2.0** | คล้าย MIT แต่มีเงื่อนไขเรื่อง patent grant เพิ่มเติม เหมาะกับโปรเจกต์ระดับองค์กร (Kubernetes ใช้ license นี้) |
| **BSD 3-Clause** | คล้าย MIT เป็นที่นิยมในโปรเจกต์ที่มาจากสาย Google/Go เอง (ตัว Go เองก็ใช้ BSD-style license) |

GitHub มีตัวช่วยสร้างไฟล์ LICENSE จาก template มาตรฐานให้ตอนสร้าง repository ใหม่โดยตรง — ไม่มีเหตุผลใดที่จะข้ามขั้นตอนนี้ไป

### 12.6 `CONTRIBUTING.md` ของตัวเอง

เมื่อ library เริ่มมีคนสนใจ contribute กลับ ให้เตรียม `CONTRIBUTING.md` ของตัวเองไว้ล่วงหน้า (แม้จะสั้นเพียงไม่กี่บรรทัด) บอกวิธีรัน test, มาตรฐาน commit message ที่ต้องการ, และ Code of Conduct โดยสังเขป — ทำให้ผู้ที่อยากช่วยเหลือรู้จุดเริ่มต้นได้ทันทีโดยไม่ต้องถามซ้ำๆ

### 12.7 Template และ Automation ที่ช่วยลดภาระ Maintainer

โปรเจกต์ที่เตรียมตัวดีตั้งแต่ต้นใช้ไฟล์ template มาตรฐานของ GitHub เพื่อให้ contributor ให้ข้อมูลที่จำเป็นครบตั้งแต่ครั้งแรก ลดรอบการถามไปมา:

```
.github/
├── ISSUE_TEMPLATE/
│   ├── bug_report.md
│   └── feature_request.md
├── PULL_REQUEST_TEMPLATE.md
├── workflows/
│   └── ci.yml          # ต่อยอดจาก Part 098
└── dependabot.yml
```

`.github/dependabot.yml` ตั้งค่าให้ GitHub เปิด PR อัปเดต dependency ให้อัตโนมัติเป็นประจำ (ทบทวนแนวคิดจาก **Part 106** หัวข้อ `govulncheck` vs Dependabot):

```yaml
version: 2
updates:
  - package-ecosystem: "gomod"
    directory: "/"
    schedule:
      interval: "weekly"
```

การเตรียม automation เหล่านี้ตั้งแต่ต้นทำให้ maintainer มีเวลาไปโฟกัสกับการตัดสินใจเชิง design แทนที่จะเสียเวลากับงาน routine ที่ automate ได้

## สรุปสิ่งที่ได้เรียนในบทนี้

- การ contribute ให้ open source เร่งการเติบโตผ่าน 4 ช่องทาง: อ่านโค้ดคุณภาพสูง, ได้ feedback จากคนเก่งกว่า, ฝึกสื่อสารข้ามบริบท, และสร้าง portfolio ที่ตรวจสอบได้จริง
- เริ่มหา first issue จาก label `good first issue`/`help wanted` หรือดีกว่านั้นคือเริ่มจาก dependency ที่ใช้อยู่แล้วในโปรเจกต์ของตัวเอง
- Workflow มาตรฐานคือ fork → branch → commit เล็กๆ ที่มีความหมาย → sync กับ upstream → เปิด PR พร้อม description ที่อธิบาย what/why/how/testing ครบถ้วน
- ต้องรัน `gofmt`, `go vet`, linter, และ test ให้ผ่านเองก่อนเปิด PR เสมอ — อย่าปล่อยให้ CI เป็นด่านแรกที่จับข้อผิดพลาดพื้นฐาน
- รับ feedback จาก code review อย่างสร้างสรรค์: ไม่ตีความเป็นเรื่องส่วนตัว, ถามเมื่อไม่เข้าใจ, reply ยืนยันเมื่อแก้แล้ว
- สำหรับงานที่ไม่เล็ก **เปิด discussion บน issue ก่อนลงมือเขียนโค้ดเสมอ** เพื่อป้องกันการเสียเวลาทำงานที่ไม่ตรงทิศทางของโปรเจกต์
- อ่าน `CONTRIBUTING.md` ของแต่ละโปรเจกต์เสมอก่อนเริ่ม เพราะกติกาต่างกันในรายละเอียดแม้จะเป็นภาษา Go เหมือนกัน
- ตัวภาษา Go เอง (`golang/go`) ใช้ **Gerrit** ผ่านเครื่องมือ `git-codereview` ต่างจากโปรเจกต์ Go ทั่วไปที่ใช้ GitHub PR มาตรฐาน
- การเปลี่ยนแปลงที่กระทบตัวภาษา/standard library ต้องผ่าน **Go Proposal Process** ที่เข้มงวด เพื่อปกป้อง Go 1 Compatibility Promise
- การก้าวจาก contributor สู่ maintainer ต้องเพิ่มทักษะ triage issue, รีวิว PR ของคนอื่นอย่างสร้างสรรค์ และรับมือความขัดแย้งในชุมชนอย่างโปร่งใสและเสมอภาค
- เริ่ม open source library ของตัวเองให้ดีตั้งแต่วันแรก: README ที่มี badge และตัวอย่างใช้งานจริง, doc comment ที่เป็นมิตรกับ `go doc`/pkg.go.dev, semantic versioning ตั้งแต่ v0.1.0, CI ตั้งแต่ commit แรก, และไฟล์ LICENSE ที่ชัดเจน

## แบบฝึกหัดท้ายบท

1. ค้นหา GitHub issue ที่ติด label `good first issue` ใน repository ภาษา Go จริง 3 โปรเจกต์ที่แตกต่างกัน อ่านรายละเอียดแต่ละ issue แล้วประเมินว่าอันไหนเหมาะกับระดับความรู้ปัจจุบันของตัวเองที่สุด พร้อมให้เหตุผล
2. เลือก dependency หนึ่งตัวที่เคยใช้ในบทก่อนๆ ของหลักสูตรนี้ (เช่น Gin, GORM, `golang-jwt/jwt`) เปิดอ่าน `CONTRIBUTING.md` ของโปรเจกต์นั้นจริง สรุปว่ามีข้อกำหนดพิเศษอะไรบ้างที่ต่างจากขั้นตอนมาตรฐานในบทนี้
3. ลองทำ workflow เต็มรูปแบบในหัวข้อ 3-5 จริงกับ repository ทดลองของตัวเอง (สร้าง repository เปล่าไว้ทดสอบ แล้วให้เพื่อนหรือบัญชีที่สองมาเปิด PR ใส่) ฝึกความคุ้นเคยกับขั้นตอน fork-branch-PR ก่อนไปลองกับโปรเจกต์จริง
4. อ่าน [go.dev/doc/contribute](https://go.dev/doc/contribute) ฉบับเต็ม แล้วสรุปเป็นข้อๆ ว่าขั้นตอนการส่ง patch แรกให้ตัวภาษา Go เองต่างจาก GitHub PR ทั่วไปที่ตรงไหนบ้าง นอกเหนือจากที่บทนี้กล่าวถึง
5. สร้าง Go library เล็กๆ ของตัวเอง (แม้จะเป็นแค่ utility function ไม่กี่ตัว) แล้วทำตาม checklist ในหัวข้อ 12 ให้ครบทุกข้อ: README พร้อม badge, doc comment ครบทุก exported identifier, tag `v0.1.0`, GitHub Actions CI, `.github/dependabot.yml`, และไฟล์ LICENSE
6. ค้นคว้าเพิ่มเติมเรื่อง proposal ที่เคยถูก `Declined` ใน Go Proposal Process (ค้นหาใน `golang/go` issue พร้อม label `Proposal` และ `Declined`) เลือกมาหนึ่งอันแล้วสรุปว่าทำไมทีม Go ถึงตัดสินใจปฏิเสธ ข้อมูลนี้ช่วยให้เข้าใจปรัชญาการออกแบบของ Go ลึกขึ้นได้อย่างไร
7. เลือก issue หนึ่งอันในโปรเจกต์ที่สนใจ (ไม่ต้อง merge จริง) แล้วฝึกเขียนคอมเมนต์แบบหัวข้อ 7 เสนอแนวทางแก้ก่อนลงมือเขียนโค้ดจริง สังเกตว่าการเขียนคอมเมนต์แบบนี้บังคับให้คิดแนวทางให้ตกผลึกก่อนเขียนโค้ดอย่างไร
