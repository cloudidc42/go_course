## 1. ทบทวนปรัชญา concurrency ของ Go จาก Part 001

ใน Part 001 เราทิ้งท้ายไว้ด้วยประโยคสำคัญที่สุดประโยคหนึ่งในโลกของ Go:

> "Do not communicate by sharing memory; share memory by communicating."

แปลตรงตัวคือ "อย่าสื่อสารกันด้วยการแชร์หน่วยความจำ แต่จงแชร์หน่วยความจำด้วยการสื่อสาร" ตอนนั้นเราบอกไว้แค่ว่านี่คือหัวใจของแนวคิด concurrency ใน Go และจะเรียนเจาะลึกใน**ภาคที่ 3** — ถึงเวลานั้นแล้ว

ในภาษาโปรแกรมมิ่งสายเก่าอย่าง C++, Java หรือ Python การเขียนโปรแกรมที่ทำงานหลายอย่างพร้อมกัน (concurrent) มักเริ่มต้นด้วยแนวคิด **shared memory**: สร้างตัวแปรหรือโครงสร้างข้อมูลหนึ่งชุด แล้วให้หลาย thread เข้าถึงตัวแปรนั้นพร้อมกัน จากนั้นใช้ lock (mutex) มาป้องกันไม่ให้สอง thread เขียนพร้อมกันจนข้อมูลเสียหาย วิธีนี้ใช้งานได้จริง แต่มีปัญหาเรื้อรัง: ลืมล็อกจุดใดจุดหนึ่งก็เกิด race condition, ล็อกผิดลำดับก็เกิด deadlock และยิ่งโปรแกรมใหญ่ขึ้น การไล่ตามว่าใครถืออะไรอยู่ก็ยิ่งซับซ้อนแบบทวีคูณ

Go เสนอแนวทางอีกแบบเป็นทางเลือกหลัก (ไม่ได้ปิดกั้นแนวทาง shared memory — Go ก็มี `sync.Mutex` ให้ใช้เหมือนกัน ซึ่งเราจะเรียนใน Part 039): ให้หน่วยงานที่ทำงานพร้อมกัน ซึ่งเรียกว่า **goroutine** สื่อสารกันผ่าน **channel** แทนที่จะแชร์ตัวแปรตรงๆ พูดง่ายๆ คือ แทนที่จะให้สอง goroutine แย่งกันเขียนตัวแปรร่วมกัน เราส่ง "ข้อมูล" ผ่าน channel จาก goroutine หนึ่งไปอีก goroutine หนึ่งแทน ความเป็นเจ้าของข้อมูล (ownership) จึงถูกส่งต่อไปพร้อมกับข้อมูลนั้นเอง ไม่มีใครสองคนถือกรรมสิทธิ์ในข้อมูลชิ้นเดียวกันพร้อมกัน

นี่ไม่ใช่แค่คำขวัญสวยหรู — มันสะท้อนออกมาเป็น 2 building block หลักที่เราจะเรียนตลอดภาคนี้:

- **Goroutine** (บทนี้): หน่วยงานที่ทำงานพร้อมกันได้ เบามาก สร้างได้เป็นหลักแสนหลักล้านตัวในโปรแกรมเดียว
- **Channel** (Part 037): ท่อสื่อสารที่ปลอดภัยสำหรับส่งข้อมูลระหว่าง goroutine

เริ่มจาก goroutine กันก่อน

## 2. Goroutine คืออะไร

**Goroutine** คือฟังก์ชันที่ทำงานพร้อมกันกับฟังก์ชันอื่นๆ ในโปรแกรมเดียวกัน โดยถูกจัดการ (schedule) โดย **Go runtime** เอง ไม่ใช่โดยระบบปฏิบัติการโดยตรง

นิยามสั้นๆ ที่ควรจำ:

> Goroutine คือ **lightweight thread ที่บริหารจัดการโดย Go runtime** — เบากว่า OS thread มาก ทำให้สร้างได้จำนวนมหาศาลโดยไม่กระทบ performance

คำว่า "lightweight" ตรงนี้ไม่ใช่การพูดเกินจริง เดี๋ยวหัวข้อถัดไปจะแสดงตัวเลขเปรียบเทียบให้เห็นชัดๆ

goroutine ไม่ใช่ concept ที่ Go คิดค้นขึ้นมาใหม่ทั้งหมด — มันคล้ายกับ "green thread" หรือ "coroutine" ที่มีในภาษาอื่น (เช่น Erlang's process, หรือ coroutine ใน Lua) แต่ Go เอาแนวคิดนี้มาผนวกเข้ากับ syntax ที่เรียบง่ายที่สุดเท่าที่จะทำได้ — เพียงคำเดียวคือ `go`

## 3. Goroutine เทียบกับ OS Thread: ทำไมถึงเบากว่ามาก

เพื่อเข้าใจว่าทำไม Go ถึงกล้าบอกให้โปรแกรมเมอร์ "สร้าง goroutine ได้ตามสบาย" มาเปรียบเทียบกับ thread ระดับ OS แบบดั้งเดิมกัน:

| คุณสมบัติ | OS Thread (เช่น pthread) | Goroutine |
|---|---|---|
| ขนาด stack เริ่มต้น | คงที่ ปกติ 1–8 MB ต่อ thread | เริ่มต้นเล็กมากเพียง **~2 KB** และ **ขยายได้เอง (growable)** ตามความจำเป็น |
| ผู้จัดการ scheduling | Kernel ของระบบปฏิบัติการ | Go runtime scheduler (ทำงานใน user space) |
| ต้นทุนการสร้าง/ทำลาย | สูง (ต้องเรียก system call) | ต่ำมาก (จัดการภายใน process เดียว ไม่ต้องสลับเข้า kernel) |
| จำนวนที่สร้างได้ในทางปฏิบัติ | หลักพันถึงหลักหมื่น (ก่อนจะกิน memory/ทรัพยากรจนระบบมีปัญหา) | หลักแสนถึงหลักล้าน ในเครื่องทั่วไป |
| การสลับ context | สลับผ่าน kernel (costly) | สลับใน user space โดย Go scheduler (เร็วกว่ามาก) |

จุดสำคัญที่สุดคือเรื่อง **stack ที่ขยายได้ (growable stack)**: OS thread ต้องจองพื้นที่ stack ขนาดคงที่ตั้งแต่แรก (มักตั้งไว้สูงเผื่อไว้ก่อน เพราะขยายทีหลังทำยาก) แต่ goroutine เริ่มต้นด้วย stack เพียงประมาณ **2 กิโลไบต์** เท่านั้น แล้ว Go runtime จะคอยตรวจสอบและ **ขยาย (grow)** หรือ **ย่อ (shrink)** stack นี้โดยอัตโนมัติตามความจำเป็นระหว่างการทำงาน (โดยการจอง stack ก้อนใหม่ที่ใหญ่ขึ้น คัดลอกข้อมูลเดิมไป แล้วปรับ pointer ทั้งหมดให้ชี้ตำแหน่งใหม่ — ทำได้เพราะ Go runtime รู้จักทุก pointer ในโปรแกรมของตัวเอง) ผลคือโปรแกรมหนึ่งตัวสามารถมี goroutine เป็นแสนเป็นล้านตัวพร้อมกันได้โดยใช้ memory รวมกันเพียงไม่กี่ร้อยเมกะไบต์ ในขณะที่ถ้าเป็น OS thread จำนวนเท่ากันจะกิน memory หลักหลายสิบกิกะไบต์จนระบบล่มไปก่อน

นี่คือเหตุผลที่ระบบอย่าง web server ใน Go มักออกแบบให้ **spawn goroutine ใหม่ 1 ตัวต่อ 1 request ที่เข้ามา** ได้อย่างสบายใจ (จะเห็นแพทเทิร์นนี้ชัดเจนใน Part 047 เรื่อง HTTP Server) ซึ่งถ้าเป็นภาษาที่ใช้ OS thread ตรงๆ การทำแบบนี้จะเป็นปัญหาเรื่อง scalability ทันทีเมื่อ traffic สูงขึ้น

## 4. เปิด goroutine ด้วย `go`

Syntax เรียบง่ายที่สุดเท่าที่จะเป็นไปได้: ใส่ keyword `go` ไว้หน้าการเรียกฟังก์ชัน

```go
package main

import (
	"fmt"
	"time"
)

func sayHello(name string) {
	fmt.Println("สวัสดี,", name)
}

func main() {
	go sayHello("Goroutine A")
	go sayHello("Goroutine B")
	fmt.Println("main: สั่ง goroutine ไปแล้ว")

	time.Sleep(100 * time.Millisecond) // แค่เพื่อสาธิต — จะอธิบายว่าทำไมวิธีนี้ไม่ดีในหัวข้อถัดไป
}
```

ผลลัพธ์ (ลำดับอาจเปลี่ยนไปในแต่ละครั้งที่รัน):

```
main: สั่ง goroutine ไปแล้ว
สวัสดี, Goroutine A
สวัสดี, Goroutine B
```

หรืออาจได้:

```
สวัสดี, Goroutine A
main: สั่ง goroutine ไปแล้ว
สวัสดี, Goroutine B
```

สังเกตสิ่งสำคัญ:

1. `go sayHello("Goroutine A")` **ไม่รอ** ให้ `sayHello` ทำงานเสร็จ — มันแค่ "สั่ง" ให้ Go runtime เอาฟังก์ชันนี้ไปเข้าคิวรันแบบ concurrent แล้วโปรแกรมก็ทำงานบรรทัดถัดไปทันที
2. **ลำดับการพิมพ์ไม่แน่นอน (nondeterministic)** ระหว่าง `main: สั่ง goroutine ไปแล้ว`, `สวัสดี, Goroutine A`, และ `สวัสดี, Goroutine B` — ทั้งสามบรรทัดนี้แข่งกันทำงาน ใครถึงคิวก่อนก็พิมพ์ก่อน ลองรันโค้ดนี้ซ้ำๆ หลายครั้งจะเห็นลำดับสลับกันไปมา
3. argument ของฟังก์ชัน (`"Goroutine A"`, `"Goroutine B"`) ถูก**ประเมินค่าทันที**ตอนเขียน `go sayHello(...)` (ไม่ใช่ตอน goroutine เริ่มทำงานจริง) นี่เป็นเรื่องสำคัญที่จะพูดถึงอีกครั้งในหัวข้อ closure ด้านล่าง

> **ข้อสังเกต**: `go f()` ไม่คืนค่าอะไรเลย (ไม่มี return value, ไม่มี handle หรือ "goroutine object" ให้เก็บไว้อ้างอิงทีหลังแบบ `Thread` object ใน Java) เมื่อ spawn ไปแล้ว คุณไม่มีทางสั่ง "หยุด goroutine ตัวนี้" จากภายนอกโดยตรง — ต้องออกแบบให้ goroutine เองคอยเช็คสัญญาณเพื่อหยุดตัวเอง ซึ่งเป็นแพทเทิร์นที่เราจะเรียนผ่าน channel และ `context` ใน Part 038 และ Part 043

## 5. กับดักอันดับหนึ่ง: `main()` จบ ไม่รอ goroutine

นี่คือกับดักที่โปรแกรมเมอร์ Go มือใหม่แทบทุกคนต้องเจอะเจอ: **เมื่อฟังก์ชัน `main()` return โปรแกรมทั้งหมดจบทันที ไม่สนใจว่ามี goroutine ตัวไหนกำลังทำงานค้างอยู่หรือไม่**

ลองดูตัวอย่างนี้:

```go
package main

import "fmt"

func main() {
	go func() {
		fmt.Println("ข้อความนี้อาจไม่ถูกพิมพ์เลย!")
	}()

	fmt.Println("main: จบการทำงานทันที")
	// main() return ณ จุดนี้ -- โปรแกรมทั้งหมดจบทันที ไม่สนใจว่า goroutine ข้างบนทำงานเสร็จหรือยัง
}
```

รันโปรแกรมนี้ซ้ำๆ หลายสิบครั้งจะเห็นผลลัพธ์ส่วนใหญ่เป็นแบบนี้:

```
main: จบการทำงานทันที
```

โดย**ไม่มี**ข้อความ `"ข้อความนี้อาจไม่ถูกพิมพ์เลย!"` ปรากฏออกมาเลย เหตุผลคือ:

1. `go func() { ... }()` สั่งให้ Go runtime เข้าคิว goroutine ใหม่ แต่ไม่ได้เริ่มรันมันทันทีเดี๋ยวนั้น (การ schedule ต้องใช้เวลาแม้จะน้อยมากก็ตาม)
2. `fmt.Println("main: จบการทำงานทันที")` ทำงานเร็วกว่ามาก และทันทีที่บรรทัดนี้จบ ฟังก์ชัน `main()` ก็ return
3. เมื่อ `main()` return **กระบวนการ (process) ทั้งหมดของโปรแกรมจบลงทันที** — ไม่ว่าจะมี goroutine อื่นกำลังทำงานอยู่กี่ตัวก็ตาม พวกมันจะถูกฆ่าทิ้งไปพร้อมกับ process โดยไม่มีการรอ ไม่มีการแจ้งเตือน ไม่มีการ cleanup ใดๆ

แต่ถ้าลองรันซ้ำสัก 20-30 ครั้งติดต่อกัน จะพบว่า**บางครั้ง** (นานๆ ครั้ง ขึ้นกับภาระงานของเครื่องตอนนั้น) ข้อความ `"ข้อความนี้อาจไม่ถูกพิมพ์เลย!"` ก็หลุดออกมาได้เหมือนกัน — นี่ไม่ใช่ความขัดแย้งในตัวเอง แต่เป็น**ประเด็นสำคัญที่สุด**ของหัวข้อนี้: ผลลัพธ์ของโค้ดนี้**ไม่แน่นอน (nondeterministic)** โดยสมบูรณ์ ไม่มีการรับประกันใดๆ ทั้งสิ้นว่า goroutine จะได้ทำงานทันหรือไม่ทัน — มันขึ้นอยู่กับว่า Go scheduler จะ schedule goroutine ให้ทันก่อนที่ `main()` จะ return หรือไม่ ซึ่งเป็นเรื่องของจังหวะเวลาล้วนๆ ที่โปรแกรมเมอร์ควบคุมไม่ได้และไม่ควรพึ่งพา

> **กฎเหล็กที่ต้องจำ**: Go **ไม่รอ** goroutine ที่ spawn ไว้โดยอัตโนมัติ ต่างจากภาษาที่มี garbage-collected finalizer หรือกลไก join แบบบังคับ — ถ้าอยากให้โปรแกรมรอ ต้อง**บอกมันอย่างชัดเจน**ว่าต้องรออะไร รอนานแค่ไหน และไม่ว่า goroutine จะมีโอกาสได้พิมพ์ทันหรือไม่ทันก็ตาม **ห้ามเขียนโค้ดที่พึ่งพาความบังเอิญของจังหวะเวลาแบบนี้เด็ดขาด**

คำถามคือ แล้วเราจะบอก Go ว่า "รอ goroutine นี้ให้เสร็จก่อน" ได้อย่างไร? นั่นคือหัวข้อถัดไป

## 6. ทำไมต้องมีการ "sync" — และทำไม `time.Sleep` ไม่ใช่คำตอบที่ถูกต้อง

วิธีแก้ปัญหาที่โปรแกรมเมอร์มือใหม่มักคิดถึงเป็นอันดับแรกคือ "ก็แค่หน่วงเวลาให้นานพอที่ goroutine จะทำงานเสร็จสิ" ด้วย `time.Sleep`:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	go func() {
		fmt.Println("ข้อความนี้ถูกพิมพ์เพราะเรารอด้วย time.Sleep")
	}()

	time.Sleep(50 * time.Millisecond) // วิธีนี้ "ใช้ได้" แต่เป็น bad practice -- อธิบายด้านล่าง
	fmt.Println("main: จบการทำงาน")
}
```

ผลลัพธ์:

```
ข้อความนี้ถูกพิมพ์เพราะเรารอด้วย time.Sleep
main: จบการทำงาน
```

ใช่ครับ — วิธีนี้ **"ใช้ได้"** ในความหมายที่ว่ามันทำให้โปรแกรมรอนานพอที่ goroutine จะทำงานเสร็จก่อนที่ `main()` จะ return จริง แต่นี่คือ **anti-pattern ที่ไม่ควรใช้ในโค้ดจริงเด็ดขาด** ด้วยเหตุผลดังนี้:

1. **ไม่มีการรับประกันเวลาที่แน่นอน**: เราไม่รู้ว่า goroutine จะใช้เวลาเท่าไรจริงๆ ถ้าเครื่องช้ากว่าที่คาด หรือระบบมีภาระงานหนักตอนนั้นพอดี 50ms อาจไม่พอ ทำให้เกิดบั๊กที่ขึ้นอยู่กับสภาพแวดล้อม (flaky) ซึ่งเป็นบั๊กที่วินิจฉัยยากที่สุดประเภทหนึ่ง
2. **สิ้นเปลืองเวลาโดยไม่จำเป็น**: ถ้า goroutine ทำงานเสร็จใน 2ms แต่เรา sleep ไว้ 50ms โปรแกรมก็เสียเวลาไปโดยเปล่าประโยชน์ถึง 48ms ทุกครั้งที่รัน ถ้ามี pattern นี้ซ้ำๆ หลายจุดในโปรแกรมใหญ่ ความช้าจะสะสมมหาศาล
3. **ไม่ scale**: ถ้ามี goroutine 100 ตัวที่ใช้เวลาไม่เท่ากัน จะ sleep นานแค่ไหนถึงจะ "พอดี" สำหรับทุกตัว? ไม่มีคำตอบที่ถูกต้องตายตัว

สิ่งที่เราต้องการจริงๆ ไม่ใช่ "รอเวลาที่คาดเดา" แต่คือ **กลไกที่ goroutine บอกกับ main โดยตรงว่า "ฉันทำงานเสร็จแล้วนะ"** และให้ `main()` รอสัญญาณนั้นแบบแม่นยำ ไม่ต้องเดา

Go มีเครื่องมือมาตรฐานสำหรับเรื่องนี้โดยเฉพาะคือ **`sync.WaitGroup`** ซึ่งให้ `main()` (หรือ goroutine ใดๆ) รอจนกว่า goroutine กลุ่มหนึ่งจะรายงานตัวว่า "ทำงานเสร็จแล้วครบทุกตัว" แบบแม่นยำ ไม่ต้องเดาเวลา — เราจะเรียนเจาะลึกเรื่อง `sync.WaitGroup` แบบเต็มรูปแบบใน **Part 039** อีกทางเลือกหนึ่งที่ทรงพลังไม่แพ้กันคือการใช้ **channel** เพื่อรอสัญญาณ ซึ่งจะเรียนใน **Part 037** ที่กำลังจะถึง

สำหรับตอนนี้ ขอให้จำหลักการไว้ก่อนว่า: **`time.Sleep` เป็นเครื่องมือสาธิตแนวคิดเท่านั้น ไม่ใช่เครื่องมือ synchronization ที่ใช้ในโค้ด production**

## 7. Goroutine Leak: กับดักที่มองไม่เห็นและอันตรายกว่าที่คิด

ก่อนไปดูเรื่อง scheduler ขอแวะพูดถึงปัญหาอีกแบบหนึ่งที่ตรงข้ามกับหัวข้อ 5 โดยสิ้นเชิง: แทนที่โปรแกรมจะจบเร็วเกินไปจนไม่รอ goroutine บางครั้งปัญหากลับเป็นด้านตรงข้าม — **goroutine ที่ไม่มีวันจบเลย** เรียกปัญหานี้ว่า **goroutine leak**

> **Goroutine Leak** คือสถานการณ์ที่ goroutine หนึ่งถูก block อยู่ตลอดไป (เช่น รอรับค่าจาก channel ที่ไม่มีใครส่งค่าเข้ามาอีกแล้วและไม่มีใครปิด) โดยไม่มีทางจบการทำงานได้เอง ทำให้มันค้างอยู่ในหน่วยความจำไปตลอดอายุของโปรแกรม

ตัวอย่างโค้ดที่ทำให้เกิด leak:

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// leaky สร้าง goroutine ที่รอรับค่าจาก channel ที่ไม่มีใครส่งค่าเข้ามาเลย
// และไม่มีใครปิด channel นี้ด้วย -- goroutine นี้จะ block รออยู่ "ตลอดไป"
func leaky() {
	ch := make(chan int) // ไม่มีใครส่งค่าเข้ามา และไม่มีใคร close
	go func() {
		v := <-ch // block ตลอดไป -- goroutine นี้ไม่มีวันจบ
		fmt.Println("ไม่มีวันมาถึงตรงนี้:", v)
	}()
	// ฟังก์ชัน leaky() จบการทำงานแล้ว แต่ goroutine ข้างในยังค้างอยู่ตลอดไป
}

func main() {
	fmt.Println("จำนวน goroutine ก่อนเรียก leaky:", runtime.NumGoroutine())

	for i := 0; i < 5; i++ {
		leaky()
	}

	time.Sleep(50 * time.Millisecond) // รอให้ goroutine ถูก schedule ให้ครบก่อนนับ
	fmt.Println("จำนวน goroutine หลังเรียก leaky 5 ครั้ง:", runtime.NumGoroutine())
	fmt.Println("goroutine เหล่านี้จะค้างอยู่แบบนี้ไปตลอดอายุโปรแกรม กินหน่วยความจำไปเรื่อยๆ โดยไม่มีวันถูกเก็บกวาด")
}
```

ผลลัพธ์:

```
จำนวน goroutine ก่อนเรียก leaky: 1
จำนวน goroutine หลังเรียก leaky 5 ครั้ง: 6
goroutine เหล่านี้จะค้างอยู่แบบนี้ไปตลอดอายุโปรแกรม กินหน่วยความจำไปเรื่อยๆ โดยไม่มีวันถูกเก็บกวาด
```

สังเกตว่าจำนวน goroutine เพิ่มจาก 1 เป็น 6 ทันที (goroutine หลักของ `main` เอง 1 ตัว บวกกับ 5 ตัวที่ leak) และ**จะไม่มีวันลดลงอีกเลย** เพราะแต่ละ goroutine ยัง block รออยู่ที่ `<-ch` ตลอดไป — คำสั่ง `runtime.NumGoroutine()` ที่ใช้ในตัวอย่างนี้เป็นเครื่องมือที่มีประโยชน์มากสำหรับตรวจสอบว่าโปรแกรมมี goroutine leak หรือไม่ (ถ้าตัวเลขนี้เพิ่มขึ้นเรื่อยๆ ไม่มีทีท่าจะลดลงระหว่างที่โปรแกรมทำงานปกติ นั่นคือสัญญาณเตือนที่ชัดเจน)

ทำไม goroutine leak ถึงเป็นปัญหาร้ายแรง แม้แต่ละตัวจะใช้ memory แค่ไม่กี่กิโลไบต์ (ตามที่เรียนในหัวข้อ 3)? เพราะในระบบที่ทำงานต่อเนื่องเป็นเวลานาน (เช่น web server ที่รันตลอด 24 ชั่วโมง) ถ้ามีจุดใดจุดหนึ่งในโค้ดที่สร้าง leak แบบนี้ซ้ำๆ ทุกครั้งที่มี request เข้ามา (เช่น สร้าง goroutine ที่รอ channel ซึ่งบางเงื่อนไขไม่มีวันถูกส่งค่าเข้ามา) จำนวน goroutine ที่ leak จะ**สะสมเพิ่มขึ้นเรื่อยๆ ไม่มีที่สิ้นสุด** จนในที่สุด memory ของระบบหมดและโปรแกรมล่ม — เป็นปัญหาประเภทที่มักไม่ปรากฏให้เห็นตอนพัฒนา (เพราะทดสอบสั้นๆ ไม่ทันเห็นผล) แต่จะโผล่มาเป็นปัญหาใหญ่ใน production หลังรันไปนานหลายวันหรือหลายสัปดาห์

สาเหตุที่พบบ่อยที่สุดของ goroutine leak มักเป็นหนึ่งในนี้:

1. **รอรับ/ส่งค่าจาก channel ที่ไม่มีวันมีคู่มารับ/ส่งด้วยอีกฝั่ง** (เหมือนตัวอย่างข้างต้น)
2. **ลืมใส่กลไกยกเลิก (cancellation)** ทำให้ goroutine ที่ควรหยุดเมื่อไม่ต้องการผลลัพธ์แล้ว ยังคงทำงานต่อไปเรื่อยๆ — นี่คือเหตุผลสำคัญที่ต้องออกแบบให้ทุก goroutine ระยะยาวมีทาง "ออก" เสมอ (ตามที่ได้กล่าวถึงในหัวข้อ 11) ซึ่งมักทำผ่าน `context` (Part 032) ร่วมกับ `select` (Part 038)
3. **`range` บน channel ที่ไม่เคยถูกปิด** ตามที่ได้เกริ่นไว้ใน Part 037 ว่าถ้าลืม `close()` channel ที่ฝั่งรับใช้ `range` อยู่ ฝั่งรับจะค้างรอตลอดไป

การป้องกัน goroutine leak อย่างเป็นระบบ (ผ่าน `context` และแพทเทิร์นการยกเลิกที่ถูกต้อง) เป็นหัวข้อที่เราจะกลับมาเจาะลึกอีกครั้งอย่างละเอียดใน **Part 043: Context กับ Concurrency**

## 8. Go Scheduler และโมเดล M:N

เพื่อให้เข้าใจว่าทำไม goroutine ถึงเบาและมีประสิทธิภาพขนาดนี้ ต้องเข้าใจภาพรวมของ **Go scheduler** ในระดับแนวคิด (conceptual level — รายละเอียดเชิงลึกระดับ internals ไม่ได้อยู่ในขอบเขตของภาคนี้)

Go ใช้โมเดลที่เรียกว่า **M:N scheduling** ซึ่งหมายถึงการ map **M** goroutine เข้ากับ **N** OS thread โดยที่ M มักจะมากกว่า N มาก (เช่น อาจมี goroutine หลักแสนตัว วิ่งอยู่บน OS thread เพียงหลักสิบตัว) องค์ประกอบหลัก 3 ตัวในโมเดลนี้ (มักเรียกว่า **G-M-P model**):

- **G (Goroutine)**: หน่วยงานที่ต้องการทำงาน — คือ goroutine ที่เราสร้างด้วย `go f()`
- **M (Machine)**: OS thread จริงๆ ที่ระบบปฏิบัติการมองเห็นและจัดสรร CPU ให้
- **P (Processor)**: บริบทการทำงานเสมือน (logical processor) ที่ถือคิวของ goroutine ที่พร้อมทำงาน (run queue) — จำนวน P ถูกกำหนดโดยค่า `GOMAXPROCS`

แนวคิดคร่าวๆ คือ: goroutine (G) แต่ละตัวไม่ได้ผูกติดกับ OS thread (M) ตัวใดตัวหนึ่งตายตัว แต่จะถูก **multiplex** (สลับสับเปลี่ยน) ไปมาระหว่าง OS thread ที่มีอยู่ผ่านตัวกลางคือ P เมื่อ goroutine หนึ่งต้องรอ (เช่น รอ I/O, รอ channel, หรือถูก sleep) Go scheduler จะดึง goroutine ตัวถัดไปในคิวมารันบน OS thread นั้นแทนทันที โดยไม่ต้องรอให้ OS เข้ามาช่วยสลับ (ซึ่งมี cost สูงกว่ามาก) การสลับ (context switch) ระหว่าง goroutine จึงเกิดขึ้นใน **user space** ล้วนๆ และเร็วกว่าการสลับ OS thread หลายเท่าตัว

ข้อดีของโมเดลนี้:

- โปรแกรมเมอร์**ไม่ต้องคิดเรื่อง thread pool เองเลย** — แค่เปิด goroutine ตามต้องการ Go scheduler จัดการ mapping ไปยัง OS thread ให้อัตโนมัติ
- เมื่อ goroutine ติด I/O (เช่น รอ network response) scheduler จะสลับไปรัน goroutine อื่นบน OS thread เดียวกันได้ทันที ทำให้ CPU ไม่ว่างงานโดยเปล่าประโยชน์
- จำนวน OS thread ที่ใช้จริงมักน้อยกว่าจำนวน goroutine มาก ทำให้ overhead ของระบบต่ำ

นี่คือกลไกเบื้องหลังที่ทำให้ประโยคเปิดหัวข้อของ Go เป็นจริงได้: "เขียนโค้ด concurrent ง่ายๆ ด้วย `go f()` แล้วปล่อยให้ runtime จัดการที่เหลือ"

## 9. GOMAXPROCS คืออะไร

`GOMAXPROCS` คือค่าที่กำหนดว่า Go runtime จะใช้ OS thread กี่ตัว**พร้อมกัน**ในการรันโค้ด Go จริงๆ (พูดให้แม่นยำกว่านั้นคือ จำนวน P สูงสุดในโมเดล G-M-P ด้านบน) ค่านี้ **default เท่ากับจำนวน CPU logical core ของเครื่องที่รันโปรแกรมอยู่**

ดูค่าปัจจุบันและปรับค่าได้ผ่านแพ็กเกจ `runtime`:

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("จำนวน CPU logical core:", runtime.NumCPU())
	fmt.Println("ค่า GOMAXPROCS ปัจจุบัน:", runtime.GOMAXPROCS(0)) // เรียกด้วย 0 = แค่ query ไม่เปลี่ยนค่า

	runtime.GOMAXPROCS(2)
	fmt.Println("ตั้งค่าใหม่:", runtime.GOMAXPROCS(0))
}
```

ผลลัพธ์ (ขึ้นกับเครื่องที่รัน ตัวอย่างนี้รันบนเครื่องที่มี 4 core):

```
จำนวน CPU logical core: 4
ค่า GOMAXPROCS ปัจจุบัน: 4
ตั้งค่าใหม่: 2
```

ประเด็นสำคัญที่ต้องแยกให้ออกคือ **`GOMAXPROCS` ไม่ได้จำกัดจำนวน goroutine ที่สร้างได้** (สร้างได้เป็นล้านตัวไม่ว่า `GOMAXPROCS` จะเป็นเท่าไร) มันจำกัดแค่ **จำนวน goroutine ที่รันโค้ด Go แบบขนานจริงๆ (in parallel) ได้พร้อมกันในแต่ละขณะ** เท่านั้น ถ้ามี goroutine 1,000 ตัวแต่ `GOMAXPROCS = 4` ก็จะมีแค่ 4 goroutine ที่กำลัง "รันจริง" บน CPU ในเสี้ยววินาทีใดๆ ส่วนที่เหลือรออยู่ในคิว — Go scheduler จะสลับให้แต่ละ goroutine ได้โควตาเวลา CPU (time slice) หมุนเวียนกันไป (ทำให้ยังดู "พร้อมกัน" จากมุมมองภายนอกแม้จะไม่ได้ parallel จริงทุกตัวพร้อมกัน)

> **หมายเหตุเรื่อง terminology**: **Concurrency** (การทำงานพร้อมกันเชิงโครงสร้าง — จัดการงานหลายอย่างสลับกันได้) กับ **Parallelism** (การทำงานคู่ขนานจริงบน CPU หลาย core พร้อมกัน) เป็นคนละเรื่องกัน โปรแกรมที่มี concurrency ดี (ออกแบบด้วย goroutine/channel อย่างเหมาะสม) จะได้ประโยชน์จาก parallelism อัตโนมัติเมื่อรันบนเครื่องที่มีหลาย core โดยไม่ต้องเปลี่ยนโค้ดเลย — นี่คือคำพูดที่มีชื่อเสียงของ Rob Pike ที่ว่า "Concurrency is not Parallelism" ซึ่งควรค้นคว้าเพิ่มเติมเป็นแบบฝึกหัดท้ายบทนี้

ในทางปฏิบัติแล้ว **แทบไม่จำเป็นต้องปรับ `GOMAXPROCS` เองเลย** ค่า default (เท่ากับจำนวน core) เหมาะสมสำหรับเกือบทุกกรณีการใช้งาน การปรับค่านี้เองมักทำเฉพาะในสถานการณ์พิเศษ เช่น การรันในสภาพแวดล้อม container ที่ถูกจำกัด CPU quota ไว้ต่ำกว่าจำนวน core จริงของเครื่องแม่ (host machine)

> **ข้อควรระวังเรื่อง container/Kubernetes**: ปัญหาที่พบได้บ่อยในการ deploy โปรแกรม Go ผ่าน container คือ `runtime.NumCPU()` (ซึ่ง `GOMAXPROCS` default อ้างอิงค่านี้) มองเห็น**จำนวน core ทั้งหมดของเครื่องแม่ (host)** ไม่ใช่จำนวน core ที่ container ถูกจำกัดไว้จริงผ่าน cgroup (เช่น Kubernetes resource limit ตั้งไว้ที่ 2 core แต่เครื่องแม่มี 64 core) ผลคือ Go runtime อาจตั้ง `GOMAXPROCS` สูงเกินจริงมาก ทำให้เกิด thread contention และ scheduling overhead โดยไม่จำเป็น ในสภาพแวดล้อม container สมัยใหม่ (Go 1.21 ขึ้นไป) จึงมักเห็นการใช้แพ็กเกจ `go.uber.org/automaxprocs` หรือใช้ `GOMAXPROCS` แบบ container-aware ที่ Go เพิ่มเข้ามาเพื่อปรับค่านี้ให้ตรงกับ cgroup limit จริงโดยอัตโนมัติ — เป็นรายละเอียดระดับ deployment ที่จะเจาะลึกอีกครั้งใน **Part 095-097 (Docker และ Kubernetes)**

## 10. Closures กับ goroutine: กับดักตัวแปรในลูป (เชื่อมโยง Part 005)

จำได้ไหมว่าใน **Part 005** เรื่อง loop เราได้เกริ่นถึงกับดักที่พบบ่อยที่สุดอันดับต้นๆ ในโค้ด Go: การใช้ **closure capture ตัวแปรลูป** ร่วมกับ goroutine ตอนนั้นเราสาธิตด้วยโค้ดตัวอย่างเดียวกันบน `go.mod` สองเวอร์ชัน (1.21 กับ 1.22) และพบว่าพฤติกรรมเปลี่ยนไปโดยสิ้นเชิง

มาทบทวนสั้นๆ พร้อมโยงเข้ากับ goroutine ให้ชัดเจนขึ้น:

```go
package main

import (
	"fmt"
	"sort"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	var mu sync.Mutex
	results := make([]int, 0, 3)

	for _, v := range []int{10, 20, 30} {
		wg.Add(1)
		go func() {
			defer wg.Done()
			mu.Lock()
			results = append(results, v) // Go 1.22+: v เป็นตัวแปรใหม่ทุกรอบ ปลอดภัย
			mu.Unlock()
		}()
	}
	wg.Wait()

	sort.Ints(results)
	fmt.Println(results)
}
```

ผลลัพธ์บน `go.mod` ที่ระบุ `go 1.22` ขึ้นไป (ค่า default ของโปรเจกต์ใหม่ในปัจจุบัน):

```
[10 20 30]
```

**ทำไมโค้ดนี้ถึงเป็นตัวอย่างที่ดีของทั้ง goroutine และ closure พร้อมกัน**: ทุกครั้งที่วน loop เราสร้าง **closure** (ฟังก์ชันนิรนาม `func() { ... }` ที่ "จับ" ตัวแปรจาก scope ภายนอกมาใช้ — เรื่อง closure แบบเต็มรูปแบบอยู่ใน Part 009) ที่จับตัวแปร `v` มาใช้ข้างใน แล้วเอา closure นั้นไปรันเป็น goroutine ทันที คำถามคือ closure ตัวไหนจับ `v` ตัวไหน?

- **ก่อน Go 1.22**: `v` เป็นตัวแปรตัวเดียวถูกใช้ซ้ำทุกรอบ (reused) เพราะกว่า goroutine แต่ละตัวจะได้ถูก schedule ไปรันจริง ตัวแปร `v` ในหัว loop อาจเปลี่ยนค่าไปหลายรอบแล้ว (หรือกระทั่งวนจบลูปไปแล้วทั้งหมด) ผลคือ goroutine หลายตัวอาจเห็นค่า `v` เดียวกันคือค่าสุดท้าย ทำให้ได้ผลลัพธ์ผิดเพี้ยนเช่น `[30 30 30]`
- **ตั้งแต่ Go 1.22**: ตัวแปร `v` ถูกสร้างใหม่**ทุกรอบของลูป** (per-iteration scoping) ทำให้แต่ละ goroutine จับตัวแปรคนละตัวที่ผูกกับค่าของรอบตัวเองอย่างถูกต้อง

ถ้าโปรเจกต์ของคุณยังต้องรองรับ `go.mod` ที่ระบุเวอร์ชันต่ำกว่า 1.22 (หรือแค่ต้องการโค้ดที่ชัดเจนไม่กำกวมแม้ในเวอร์ชันใหม่) ยังใช้เทคนิคที่แนะนำใน Part 005 ได้เสมอ คือส่งค่าผ่าน parameter ของ goroutine โดยตรง:

```go
for _, v := range []int{10, 20, 30} {
	wg.Add(1)
	go func(val int) {
		defer wg.Done()
		mu.Lock()
		results = append(results, val)
		mu.Unlock()
	}(v) // ส่ง v เข้าไปเป็น argument ตอน spawn -- ค่าถูกคัดลอกทันที ไม่ใช่ capture ตัวแปรร่วม
}
```

วิธีนี้ทำงานถูกต้องไม่ว่าจะเป็น Go เวอร์ชันไหน เพราะ argument ของฟังก์ชันถูก**คัดลอกค่า**ตอนเรียก ไม่ใช่ share ตัวแปรร่วมกัน (ตามหลักการ pass-by-value ที่เรียนใน Part 008-010) — จึงเป็น pattern ที่พบเห็นได้บ่อยในโค้ด Go แม้ในปัจจุบัน แม้ปัญหาเดิมจะถูกแก้ไปแล้วโดย default ก็ตาม เพราะทำให้เจตนาของโค้ดชัดเจนขึ้นสำหรับผู้อ่าน

> **ข้อควรระวังเพิ่มเติม**: ปัญหานี้ไม่ได้เกิดเฉพาะกับ `for range` เท่านั้น การใช้ closure จับตัวแปรใดๆ ที่ **เปลี่ยนค่าได้ (mutable)** แล้วนำไปรันเป็น goroutine ล้วนมีความเสี่ยงเดียวกัน หลักการที่ปลอดภัยที่สุดเสมอคือ: **ถ้า goroutine ต้องการค่าจากภายนอก ให้ส่งผ่าน parameter อย่างชัดเจนจะปลอดภัยกว่าการพึ่งพา closure capture เสมอ**

## 11. แนวทางปฏิบัติที่ดีสำหรับ goroutine

ก่อนจบบทนี้ สรุปแนวปฏิบัติสำคัญที่ควรยึดถือเมื่อทำงานกับ goroutine (บางข้อจะลงรายละเอียดเพิ่มในบทถัดๆ ไป):

1. **อย่าปล่อยให้ `main()` จบก่อน goroutine ทำงานเสร็จโดยไม่ได้ตั้งใจ** — ใช้ `sync.WaitGroup` (Part 039) หรือ channel (Part 037) เสมอ ไม่ใช่ `time.Sleep`
2. **ทุก goroutine ที่ spawn ควรมี "ทางออก" ที่ชัดเจน** — อย่าเขียน goroutine ที่วนลูปตลอดไปโดยไม่มีกลไกให้มันหยุดได้ (จะเรียก "goroutine leak" ซึ่งกินทรัพยากรสะสมไปเรื่อยๆ)
3. **ระวังเรื่อง closure capture ตัวแปรที่เปลี่ยนแปลงได้** ตามที่อธิบายในหัวข้อ 9
4. **การเข้าถึงข้อมูลร่วมกันระหว่าง goroutine ต้องมีการป้องกัน** ไม่ว่าจะผ่าน channel (แนวทางหลักของ Go) หรือ `sync.Mutex` (Part 039) — ห้ามให้หลาย goroutine อ่าน-เขียนตัวแปรเดียวกันพร้อมกันโดยไม่มีการป้องกันเด็ดขาด (จะเรียนเรื่อง data race และเครื่องมือตรวจจับ `-race` อย่างละเอียดใน Part 039 และ Part 044)
5. **จำนวน goroutine ที่มากไม่ใช่ปัญหา** (ต่างจาก OS thread) แต่ก็ไม่ควรสร้างแบบไม่มีขอบเขตควบคุม (unbounded) เมื่อรับ input จากภายนอก เพราะยังกิน memory และ scheduler overhead อยู่ดีถ้ามากเกินไปจริงๆ — แนวคิดการจำกัดจำนวน goroutine ที่ทำงานพร้อมกันจะเรียนผ่าน **Worker Pool Pattern** ใน Part 041

## สรุปสิ่งที่ได้เรียนในบทนี้

- **Goroutine** คือ lightweight thread ที่ Go runtime จัดการเอง มี stack เริ่มต้นเล็กมาก (~2KB) และขยายได้เองตามความจำเป็น ต่างจาก OS thread ที่ stack คงที่และมีขนาดใหญ่กว่ามาก (1–8MB)
- เปิด goroutine ใหม่ด้วยการใส่ `go` หน้าการเรียกฟังก์ชัน — ไม่รอผลลัพธ์ ไม่คืนค่าอะไร และไม่มี handle ให้ควบคุมทีหลัง
- **`main()` return แล้วโปรแกรมจบทันที** โดยไม่รอ goroutine ที่ยังทำงานค้างอยู่ — นี่คือกับดักที่พบบ่อยที่สุดของมือใหม่
- `time.Sleep` ใช้สาธิตแนวคิดได้ แต่**ไม่ใช่เครื่องมือ synchronization ที่ถูกต้อง**ในโค้ด production เพราะไม่แม่นยำและสิ้นเปลือง — เครื่องมือที่ถูกต้องคือ `sync.WaitGroup` (Part 039) หรือ channel (Part 037)
- **Goroutine Leak** เกิดเมื่อ goroutine ถูก block ตลอดไปโดยไม่มีทางจบ (เช่น รอ channel ที่ไม่มีคู่ส่ง/ปิด) — สะสมนานเข้าจะทำให้โปรแกรม production กิน memory จนล่ม ตรวจสอบได้ด้วย `runtime.NumGoroutine()`
- Go scheduler ใช้โมเดล **M:N (G-M-P model)** — multiplex goroutine จำนวนมากเข้ากับ OS thread จำนวนน้อยกว่า ทำให้การสลับ context เร็วกว่าการสลับ OS thread มาก
- **`GOMAXPROCS`** กำหนดจำนวน OS thread สูงสุดที่รันโค้ด Go แบบขนานพร้อมกันได้ (default = จำนวน CPU core) แต่ไม่จำกัดจำนวน goroutine ที่สร้างได้
- **Closure ที่ capture ตัวแปรลูป** ร่วมกับ goroutine เป็นกับดักคลาสสิก — Go 1.22 แก้ปัญหานี้ด้วย per-iteration scoping แต่การส่งค่าผ่าน parameter ยังเป็นแนวทางที่ชัดเจนและปลอดภัยเสมอ

## แบบฝึกหัดท้ายบท

1. เขียนโปรแกรมที่เปิด goroutine 10 ตัว แต่ละตัวพิมพ์หมายเลขของตัวเอง (1 ถึง 10) โดยส่งหมายเลขผ่าน parameter ของ goroutine (ไม่ใช่ closure capture ตรงๆ) ใช้ `time.Sleep` รอให้ทำงานเสร็จก่อน (ยังไม่ต้องใช้ `sync.WaitGroup` ในแบบฝึกหัดข้อนี้) แล้วสังเกตว่าลำดับการพิมพ์ไม่เรียงตามหมายเลข 1-10 เสมอไป
2. ทดลองลบ `time.Sleep` ออกจากโค้ดข้อ 1 แล้วรันดูว่าเกิดอะไรขึ้น อธิบายเหตุผลด้วยคำพูดตัวเองว่าทำไมข้อความส่วนใหญ่หรือทั้งหมดถึงไม่ถูกพิมพ์
3. เขียนโปรแกรมที่จงใจสร้างกับดัก closure capture ตัวแปรลูป (เหมือนตัวอย่างใน Part 005) แล้วลองสร้างไฟล์ `go.mod` สองแบบ (`go 1.21` กับ `go 1.22`) รันโค้ดเดียวกันเทียบผลลัพธ์ดูด้วยตัวเอง
4. ค้นคว้าเพิ่มเติม: ทำไม Rob Pike ถึงพูดว่า "Concurrency is not Parallelism" — ลองหาคลิปหรือบทความ talk ของเขาเรื่องนี้มาดู แล้วสรุปเป็นคำพูดของตัวเอง 3-4 ประโยคว่าเข้าใจความแตกต่างนี้อย่างไร
5. ทดลองใช้ `runtime.NumGoroutine()` (ค้นดูเองว่าใช้อย่างไรจาก Go documentation) เขียนโปรแกรมที่เปิด goroutine จำนวนมาก (เช่น 100,000 ตัว) ที่แต่ละตัวแค่ `time.Sleep` สักครู่แล้วจบ ลองพิมพ์ค่า `runtime.NumGoroutine()` ก่อนและระหว่างที่ goroutine เหล่านั้นยังทำงานอยู่ เพื่อยืนยันด้วยตัวเองว่า Go สร้าง goroutine จำนวนมากขนาดนี้ได้จริงโดยไม่มีปัญหา
6. อธิบายด้วยคำพูดตัวเองว่าทำไมการ spawn goroutine ใหม่ 1 ตัวต่อ 1 HTTP request ที่เข้ามาใน web server ถึงเป็นแนวทางที่ทำได้จริงใน Go แต่จะเป็นปัญหาถ้าเป็นภาษาที่ใช้ OS thread ตรงๆ
7. เขียนโปรแกรมที่จงใจสร้าง goroutine leak แบบเดียวกับหัวข้อ 7 (goroutine รอรับค่าจาก channel ที่ไม่มีวันมีคนส่ง) ในลูปที่ spawn 1,000 ครั้ง แล้วพิมพ์ `runtime.NumGoroutine()` ก่อนและหลังลูป เพื่อยืนยันว่าตัวเลขเพิ่มขึ้นค้างอยู่แบบนั้นจริง จากนั้นลองแก้ไขโค้ดให้ไม่เกิด leak (เช่น ใช้ `select` กับ `default` หรือปิด channel ให้ถูกจังหวะ) แล้วยืนยันว่าตัวเลข goroutine กลับมาคงที่
